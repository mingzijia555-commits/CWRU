# CWRU 项目代码与目录简化计划（易懂版）

## 一、先说结论

现在的项目已经全部运行完成，实验结果没有问题，但代码被整理得像一个正式软件产品，而不是一份学生大作业。

主要问题不是神经网络太难，而是为了“自动运行、自动检查、自动保存、出错后继续运行”写了很多辅助代码。老师真正关心的内容其实只有五件事：

1. 数据是怎样读取和处理的；
2. 训练集、验证集、测试集是怎样划分的；
3. 三个神经网络模型是怎样搭建的；
4. 模型是怎样训练的；
5. 最后的准确率、误差和对比结果是什么。

所以，后面采用有针对性的简化：保留现有项目主结构和完整结果生成能力，只删除明确不需要的测试、缓存及部分过度工程化逻辑。已经完成的 90 组实验结果继续使用，不需要重新训练。

## 二、现在每个目录和文件是干什么的

目前真正的大作业项目位于 `CWRU` 文件夹中。其他“作业”文件夹下的 Notebook 是课程练习资料，不属于本次简化范围。

### 1. 原始数据文件夹

目录名称：`CaseWesternReserveUniversityData`

这里有 109 个 `.mat` 文件，每个文件保存一段轴承振动信号。

文件名中的常见缩写：

| 缩写 | 中文意思 |
|---|---|
| `Normal` | 正常轴承 |
| `IR` | 轴承内圈故障 |
| `OR` | 轴承外圈故障 |
| `B` | 滚动体故障 |
| `DE` | 驱动端传感器 |
| `FE` | 风扇端传感器 |
| `007/014/021/028` | 故障直径，分别表示 7、14、21、28 mil |

这个目录必须保留，不能修改原始数据。

### 2. 文件划分目录

目录名称：`splits`

作用：记录哪些数据用于训练、哪些用于挑选模型、哪些只用于最后测试。

| 英文名称 | 中文意思 |
|---|---|
| `train` | 训练集，模型用这些数据学习 |
| `val` | 验证集，用于选择训练过程中表现最好的模型 |
| `test` | 测试集，只用于计算最后结果 |
| `A/B/C` | 三套不同的数据划分，用来观察结果是否稳定 |

这个目录应当保留，但目前里面自动生成的说明和统计表太多。最终只保留记录文件名单的 6 个 JSON 文件即可。

### 3. 程序代码目录

目录名称：`cwru`

这里是项目的全部程序。现在一共拆成了 23 个 Python 文件，层次偏多。

#### 数据处理部分

|---|---|---|

#### 模型部分

目录名称：`cwru/models`

主要文件：`models.py`

作用：定义三个神经网络。

| 模型名称 | 简单解释 |
|---|---|
| `Cnn1d` | 只使用一维卷积网络识别振动信号 |
| `CnnGru` | 先用卷积提取特征，再用 GRU 学习前后时间关系 |
| `CnnLstm` | 先用卷积提取特征，再用 LSTM 学习前后时间关系 |

这部分只有约 112 行，结构并不过分复杂，基本可以原样保留。只需要补充更容易理解的中文注释。

#### 模型训练部分

目录名称：`cwru/training`

主要文件：`trainer.py`

作用：

1. 把训练数据分批送入模型；
2. 计算分类错误和故障直径误差；
3. 根据误差更新模型参数；
4. 每轮在验证集上检查效果；
5. 保存表现最好的模型。

现在还包含“训练中断后继续”“保存优化器状态”“自动调节学习率”等较复杂功能。最终改成一个更直接的 `模型训练.py`，只保留普通训练循环、验证和最佳模型保存。

#### 结果评价部分

目录名称：`cwru/evaluation`

| 当前文件 | 它的实际作用 | 后续处理 |
|---|---|---|
| `metrics.py` | 计算准确率、F1、平均绝对误差等指标 | **不改动** |
| `evaluate.py` | 加载训练好的模型，在测试集上计算结果 | **只简化这一个文件** |
| `plots.py` | 生成单组实验图和总体对比图 | **不改动** |
| `compare.py` | 收集 90 组结果，计算平均值和标准差，再生成总体对比文件 | **保留，建议不改动** |

#### `compare.py` 到底做了什么

`compare.py` 不负责训练，也不负责对单个模型进行测试。它只处理已经由 `evaluate.py` 生成的 90 份 `metrics.json`。它的工作顺序是：

1. `collect_batch_metrics()` 按照“A/B/C 划分 → 两种窗口 → 五种输入 → 三种模型”的目录顺序寻找 `metrics.json`；
2. 从每一份结果中取出准确率、F1、故障直径平均绝对误差、均方根误差等主要数字；
3. `_write_csv()` 把 90 组数字写成总表 `metrics_all.csv`；
4. `build_mean_std()` 把同一种“窗口 + 输入 + 模型”在 A、B、C 三套划分下的结果合并，计算平均值和标准差；
5. 再写出 `mean_std_summary.csv`；
6. 调用 `plots.py` 生成模型对比、窗口对比和划分对比图片；
7. `summarize_conclusions()` 找出分类效果最好和故障直径误差最小的配置，并写入 `conclusions.json`。

它最终在正式结果文件夹的 `comparisons` 子目录中生成：

- `metrics_all.csv`：90 组实验的总表；
- `mean_std_summary.csv`：A/B/C 三套划分的平均值与标准差；
- `conclusions.json`：自动整理出的最佳配置和总体比较数字；
- 9 张对比图：3 张模型对比、3 张窗口方式对比、3 张数据划分对比。

这个文件虽然接近 200 行，但每一步都直接服务于最终报告，而且它只读已经完成的指标文件，不会重新训练。它不是最应该删减的部分。因此本计划把它与 `metrics.py`、`plots.py` 一起原样保留。需要注意的是，它依赖每组结果下面仍然存在固定的路径：

```text
总结果目录/A或B或C/窗口方式/输入方案/模型名称/metrics.json
```

只要这个内部目录层次不变，把最外层从“每次按时间新建”改成“永远使用一个固定目录”，`compare.py` 就能继续原样工作。

#### 单文件预测部分

目录名称：`cwru/inference`

主要文件：`predict.py`

作用：选择一个 MAT 文件，让训练好的模型判断它是什么故障以及故障直径。

这不是报告的必需内容。如果答辩时需要现场演示，就把它简化为 `单个文件预测.py`；如果不需要现场演示，可以不放进最终提交。

#### 自动命令和批量运行部分

| 当前文件 | 它的作用 | 为什么显得工程化 |
|---|---|---|
| `cli.py` | 把所有功能包装成终端命令 | 一共设计了 7 个子命令，像正式软件 |

| `fullrun.py` | 自动依次完成 90 次训练、评价和最终汇总 | 保留，因为它串联了全部结果文件的生成 |

#### `batch.py`、`fullrun.py` 和正式结果文件夹的关系

三者不是三个互相独立的东西，实际关系如下：

```text
fullrun.py 开始运行
    ↓
调用 batch.py 创建总结果目录
    ↓
batch.py 生成 run_config.json、划分快照和总 README
    ↓
fullrun.py 循环运行 90 个组合
    ↓
trainer.py 为每组生成权重和 history.json
    ↓
evaluate.py 为每组生成 metrics.json、files.csv 和 figures
    ↓
batch.py 每完成一组就更新总 README
    ↓
fullrun.py 调用 compare.py
    ↓
compare.py 生成 comparisons 中的总表、结论和对比图
    ↓
batch.py 最后把完成时间和总体结论写入总 README
```

当前正式结果文件夹 `artifacts/full_runs/20260915_175843` 是这样形成的：

- `batch.py` 第 51～55 行取得当前时间 `20260915_175843`，创建同名文件夹；
- `batch.py` 的 `run_dir()` 决定每组结果放在 `A/no_overlap/101DE/Cnn1d` 这类目录中；
- `fullrun.py` 第 55～80 行循环 90 个组合，并把 `run_dir()` 得到的路径同时传给训练和评价函数；
- `trainer.py` 在这个路径下写模型权重和训练记录；
- `evaluate.py` 继续在同一路径下写指标、逐文件结果和图片；
- `compare.py` 最后读取这些目录并建立 `comparisons`。

因此，**按时间新建最外层文件夹只是 `batch.py` 的一个路径选择功能**。删除它不会要求删除 `fullrun.py`，也不会影响单组权重、指标、图片、总表和 README 的生成。

#### 去掉“每次新建文件夹”的推荐改法

保留 `BatchContext` 以及它生成配套文件的所有方法，只修改 `BatchContext.create()`：

- 原来：根据当前时间生成 `artifacts/full_runs/20260915_175843` 这样的新目录；
- 修改后：永远使用固定目录，例如 `artifacts/full_runs/formal_run`；
- 将 `os.makedirs(..., exist_ok=False)` 改成 `exist_ok=True`；
- 删除“目录已经存在就报错”的判断；
- `run_dir()`、`snapshot_splits()`、`write_run_config()`、`write_readme()`、`record_result()`、`finish()` 全部保留；
- `fullrun.py` 的 90 组循环和最后调用 `compare.py` 的代码全部保留；
- 只把终端提示“新批次目录”改成“正式结果目录”。

推荐使用固定子目录 `formal_run`，不要直接把 A/B/C 等内容写到 `full_runs` 根部。因为 `full_runs` 里面还要同时保留现有正式批次和旧批次，直接混放会看不清。

已经完成的 `20260915_175843` 文件夹保持原样，不重命名、不搬动。简化后的固定路径只是说明以后如果再运行，应写到 `formal_run`；目前没有再次训练的计划，所以不会实际产生它。

固定目录意味着如果以后再次完整运行，同名文件会被覆盖，而且中途停止时可能同时存在新旧文件。用户已经明确不会进行第二次训练，因此可以接受这个取舍，并在代码旁写一句中文注释说明。

#### `cache` 是怎么产生的，删除后会怎样

缓存不是 Conda、PyTorch 或系统自动生成的，而是项目代码明确指定生成的：

1. `config.py` 中的 `CACHE_DIR` 指定缓存目录为 `artifacts/cache`；
2. `config.py` 中的 `ensure_dirs()` 创建这个目录；
3. `dataset.py` 中的 `get_experiment_arrays()` 先检查对应的 `.npz` 缓存是否已经存在；
4. 如果不存在，它调用 `build_experiment_arrays()` 重新读取 MAT 信号、切窗、标准化；
5. 然后由 `np.savez_compressed()` 把这些数组写成 `.npz` 文件；
6. `prepare.py` 会依次准备 30 种“划分 × 窗口 × 输入”组合，因此会批量生成缓存；
7. `fullrun.py`、单组训练和单组评价在需要数据时也会调用同一个函数。如果缓存不存在，它们同样会重新生成。

这些缓存不包含模型训练结果，也不包含无法恢复的信息。它只是把“已经切好的信号小段”保存下来，让下一次训练或评价少等待一些时间。

现在没有第二次训练计划，所以现有 `artifacts/cache` 可以全部删除，不会影响已经保存在 `runs` 和 `full_runs` 中的权重、指标、CSV、图片或 README。`compare.py` 也完全不读取缓存。

但要区分两种做法：

- **只删除现有缓存文件夹**：现在能节省约 1.33 GB；以后若再次运行 `prepare`、训练或评价，代码会把缓存重新生成出来；
- **连缓存功能一起删除**：还需要修改 `dataset.py`，让 `get_experiment_arrays()` 每次直接调用 `build_experiment_arrays()` 并返回内存中的数据，同时从 `config.py` 的目录创建列表中移除 `CACHE_DIR`。

按“不会再训练第二次”的前提，本计划采用第二种：删除现有缓存，同时删掉缓存读取和写入逻辑。这样代码更简单，也不会在误运行时重新生成 1.33 GB 缓存。原始数据处理逻辑仍然保留。

## 三、哪些地方不能为了简单而删除

以下内容虽然看起来也像“检查代码”，但会直接影响实验是否正确，必须保留：

1. **先按完整文件划分数据，再切成 1024 点的小段。** 这样可以避免同一个原始文件同时出现在训练集和测试集中。
2. **正常轴承数据要从 48 kHz 降到 12 kHz。** 这样才能与故障数据使用相同采样率。
3. **标准化的平均值和标准差只能根据训练集计算。** 不能提前看到验证集和测试集的信息。
4. **正常轴承不参加故障直径误差计算。** 因为正常轴承没有故障直径。
5. **必须使用验证集选择最佳模型。** 不能根据测试集表现挑选模型。
6. **文件级故障直径必须来自模型预测。** 不能不小心把真实答案当作预测结果。
7. 三个数据文件存在特殊的读取规则，这些规则必须继续保留，否则可能读取错误变量。

上面这些内容是保证实验可信的基础，不属于应该删除的“过度工程化”。
